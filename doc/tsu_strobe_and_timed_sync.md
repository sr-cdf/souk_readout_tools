# TSU Strobe and Timed Sync

This note describes the 1-PPS **TSU strobe** and the firmware **timed-sync**
bring-up for the SOUK RFSoCs, and the standalone test scripts in
`scripts/timed_sync/`. It complements [timing.md](timing.md) (the PTP/chrony
clock-discipline stack) — this is the layer that turns a disciplined PHC into a
firmware telescope-time (TT) and a deterministic synchronisation pulse.

All hardware results below were confirmed in local lab testing (June 2026) on
`souk_dual_pipeline_krm` firmware v7.10.2, fabric clock 307.2 MHz, with a
**hardware-PHC grandmaster** running on a commodity workstation (serving from its
NIC's PHC, not a dedicated GPS/atomic appliance).

## Concepts

- **TSU** = the Zynq GEM **Timestamp Unit** — the Ethernet MAC's timestamp
  counter, disciplined to the grandmaster by `ptp4l`/chrony through the PHC. Its
  compare output emits a strobe.
- **TSU strobe** = a 1-pulse-per-second signal generated by programming the GEM
  TSU compare register to fire on each integer-second boundary. This is the PPS
  the firmware aligns its telescope time to (the software TT load latches on a PPS
  edge). There is no separate external PPS input.
- **Telescope time (TT)** = a firmware counter of fabric clock ticks since the
  UNIX epoch. Loaded from software on a PPS edge (`update_internal_time`), then
  free-runs on the fabric clock.
- **Timed sync** = a firmware reset+sync pulse armed to fire at a chosen future
  TT (`set_timed_sync`). The basis for synchronising multiple boards: every board
  arms the same target second.

## The strobe service

The strobe is a continuous re-arming loop (the GEM compare is one-shot, so it is
re-armed every second). It must keep running; it holds an exclusive lock so only
one instance touches the single compare register.

- `souk-tsu-strobe` — the packaged daemon (`server/tsu_strobe.py`). Run by the
  systemd service. Writes status JSON to `/run/tsu-strobe.status` every second
  (`running, pid, rearms, tsu_sec, updated_unix_s`) and logs a heartbeat.
- `tsu-strobe.service` — the systemd unit (packaged in `data/daemon/`).
- CLI control (mirrors the readout-server daemon commands):
  `souk-tsu-strobe-install`, `-start`, `-stop`, `-restart`, `-status`, `-remove`.
- The strobe runs and re-arms **regardless** of PTP/chrony — it just will not
  produce a *time-aligned* PPS until the PHC is disciplined (the service `After=`
  the timing units is only a soft ordering hint).

Strobe health is also surfaced through the timing monitor: `get_info("timing")`
includes a `strobe` section (`present/running/healthy/pid/rearms/tsu_sec/
status_age_s`) and a top-level `summary.strobe_healthy`, read from
`/run/tsu-strobe.status`.

## Test / bring-up scripts (`scripts/timed_sync/`)

Standalone scripts (no install needed; each hardcodes `FW_CONFIG`/`PIPELINE_ID`/
`CLK_HZ` at the top). They print which firmware registers and `sync.py` functions
they use. Run roughly in order; `01` must be running for `02`-`08`.

| Script | Purpose | Lab result (June 2026) |
|---|---|---|
| `01_strobe.py` | Readable test version of the strobe loop (the service runs the packaged `souk-tsu-strobe`). Prints the first 3 re-arms then runs quietly. Single-instance flock + PID. | Re-arms 1/s; TSU sec = real epoch; runs until Ctrl-C. |
| `02_check_pps.py` | Prove a PPS reaches the firmware: read the `ext_sync_tt` register (TT latched at each PPS), check the per-pulse delta. | Delta = 307,199,7xx clks = **1.000000 s** every pulse. PASS. |
| `03_set_tt.py` | Load the TT (`update_internal_time`), read the PPS-latched TT, show offset from the integer second (and a coarse system-clock check). | Latched TT **−1 µs** from the second boundary right after a fresh load. PASS. |
| `04_timed_sync.py` | The multi-board model: master reset → wait → set TT → arm `set_timed_sync` at a future second. | `set_timed_sync` arms (sensible positive countdown) and fires. (`tt_sync` read-back is an open HDL question — see below.) |
| `05_check_timing_system.py` | Confirm the readout-tools timing monitor agrees: state, `ready_for_firmware_sync`, PTP offsets — the coordinator preconditions. | `locked_to_gm`, ready, `ptp_master_offset` ~130–210 ns, `system_time_offset` ~1e-8 s. READY. |
| `06_katcp_vs_local.py` | Compare KATCP-over-localhost vs `local=True` (`/dev/mem`) register read latency and the reported boundary offset. | KATCP **~910 µs/read** vs local **~26 µs/read** (~35× faster); boundary offset transport-independent (<2 µs difference). |
| `07_tt_drift.py` | Measure how fast the TT drifts after a single load (PPS-latched offset vs time), fit ppm. | **~1.6 ppm** (≈1.6 µs/s) — the fabric oscillator vs the PHC-disciplined PPS. Linear, clean. |
| `08_arm_drift.py` | The firmware's intended drift monitor: `arm_sync()` then poll `get_drift()`. | `get_drift` reads a **flat 0** while the TT demonstrably drifts — it does **not** accumulate on this gateware (open HDL question; use `07`'s method instead). |
| `09_strobe_status.py` | Report strobe health: `systemctl is-active tsu-strobe` + the `/run/tsu-strobe.status` file. | HEALTHY iff service active, status fresh (<3 s), running. |

## Key results and consequences

- **PPS, TT load, and second-boundary alignment all work**: 1.000000 s PPS,
  TT tracks UNIX time, lands sub-2 µs on the integer second after a fresh load.
- **Transport**: use `local=True` (`/dev/mem`) for tight register polling — ~35×
  lower latency than KATCP; it does not change the measured offsets.
- **TT drifts ~1.6 ppm** after a load (fabric clock vs PPS). Consequence for the
  multi-board timed sync: a board's TT drifts ~1.6 µs per second since its last
  `update_internal_time`, so all boards must **re-discipline the TT shortly
  before arming `set_timed_sync`** (or track continuously). Because all boards
  share the same grandmaster, they agree *with each other* even if collectively
  offset from absolute UTC (acceptable with the workstation GM; the offset from true
  UTC may be ms-level and is not a fault).

## Open firmware questions

These are firmware/gateware-side items to resolve; they do not block the
bring-up above:

1. `set_timed_sync` fires but the `tt_sync` register is not updated by it, so we
   cannot yet *timestamp* where a timed sync landed. (Which sync latches
   `tt_sync`? Is the `mrst` ordering — reset before vs after the TT load —
   as intended?)
2. `get_drift()` reads a flat 0 after `arm_sync()` while the TT drifts ~1.6 ppm —
   it does not appear to be a live accumulating-drift monitor on this gateware,
   though the Sync block docstring (step 4) says to use it to observe drift.
3. Cosmetic: `update_internal_time`'s log lines labelled "NTP" are computed from
   the system clock (`time.time()`), not an NTP query.

## Client commands

The timed sync is exposed as four `client` commands. The firmware logic lives in
`firmware_lib.timed_sync_*` (ports of scripts 03/04/07); the readiness gate is
`timing.report_sync_readiness` (a port of script 05).

| Command | Purpose |
|---|---|
| `client.timed_sync_needed()` | Should this board sync, and can it? Reports TT boundary alignment plus PTP/strobe readiness (`can_sync`). Read-only. |
| `client.timed_sync_ready(target_unix_s=None, seconds_from_now=None)` | Are we ready to fire at the target second? Checks PTP, the PPS strobe, and that the target is in the future vs the server, firmware, and client clocks. Read-only. |
| `client.timed_sync_arm(target_unix_s=None, seconds_from_now=None, mrst=False, reload_tt='auto', wait=False, force=False)` | Arm `set_timed_sync` at the target (the firmware re-aligns to the PPS at fire); reloads the TT *value* only when needed (`reload_tt`). Returns once armed (fires autonomously) unless `wait=True`. Refuses unless ready, unless `force=True`. |
| `client.timed_sync_check(measure_drift=True)` | Confirm the TT is aligned (boundary offset within ~50 us) and report the live drift (~1.6 ppm). Echoes the last armed target. |

Notes:

- **Drift and alignment use the `ext_sync_tt` PPS-latched-TT offset**, not the
  firmware `tt_sync`/`get_drift` registers, which are unreliable on this gateware
  (see the open questions above, and scripts 07/08).
- `timed_sync_arm` reloads the TT *value* (`update_internal_time`, ~3-4 s on PPS
  edges) only when needed -- by default when the TT is unset or has drifted ~1 s
  (~7 days at 1.6 ppm). The per-fire PPS re-align handles sub-second drift, so a plain
  arm is fast; pass `reload_tt=True` to force a reload, `False` to skip it.
- Targets are quantised to a whole second (the PPS edge the firmware fires on).
- The `souk-tsu-strobe` service must be running and PTP locked. `timed_sync_arm`
  gates on `summary.strobe_healthy` + `ready_for_firmware_sync` first (unless
  `force=True`), so a missing strobe fails cleanly instead of hanging inside
  `update_internal_time`.

## Multi-board sync

The coordinator is deliberately trivial -- a short loop over the per-board
commands, not a new subsystem:

```python
T = time.time() + 30                      # a common target second, comfortably ahead
clients = [ReadoutClient(address=board) for board in boards]

# 1. every board must be ready to fire at the SAME second T
assert all(c.timed_sync_ready(target_unix_s=T)["ready"] for c in clients)

# 2. arm each; the firmware fires the reset+sync autonomously when its TT reaches T
for c in clients:
    c.timed_sync_arm(target_unix_s=T)

# 3. verify alignment + drift on every board
for c in clients:
    print(c.timed_sync_check())
```

`T` must be far enough ahead that every board finishes re-disciplining its TT
(~3-4 s) and arming before the edge. Because all boards share the grandmaster they
agree *with each other* even if collectively offset from absolute UTC (fine for a
coordinated sync with the workstation GM). A packaged version of this loop is the
remaining piece of work.
